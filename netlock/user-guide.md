# NetLock — гайд пользователя

Интернет-заглушка на время **без туннеля, без службы, без обязательного
админа**. Один exe (`nl.exe`) + ini рядом.

> См. также **NetOff** (`C:\proj\NetOff`) — отдельный проект с туннелем
> wintun и службой для долгосрочного контроля. NetLock — про задачу
> «заглушить интернет на заданное время».

## Три движка

| Движок | Права | Что глушит |
|---|---|---|
| `wfp` | администратор | **весь** IP-трафик (фильтры ядра на 8 слоях) |
| `fw` | администратор | **весь** IP-трафик (правила Windows Firewall через COM — запасной путь, если вырезаны `fwpmu`/`fwpuclnt.dll`) |
| `proxy` | обычный пользователь | только proxy-aware трафик: браузеры, WinHTTP/WinINet-приложения, большинство программ |

`engine = auto` (дефолт) — под админом берётся WFP с автоматическим
фолбэком на `fw`, без прав — proxy. Явный `-wfp`/`-fw` — строго выбранный
движок, без подмены.

Движок `fw` ставит block-правила `NetLock-*` по адресному пространству
«всё минус allowlist» (у Windows Firewall block бьёт allow, поэтому
считается комплемент). План правил без применения: `nl fwplan`.

> **Честное ограничение proxy-режима**: raw-сокеты (UDP, ICMP/ping,
> торренты, приложения игнорирующие системный прокси) проходят мимо.
> Гарантированная блокировка без прав в Windows невозможна в принципе —
> все точки enforcement'а (файрвол, маршруты, адаптеры) требуют админа.

## Как работает proxy-режим

1. Запоминает текущие настройки прокси в `netlock-backup.ini`.
2. Ставит системный прокси юзера на `127.0.0.1:17887`, где работает
   встроенный микросервер: принимает соединение и сразу отвечает
   `HTTP/1.1 403`. Живой отказ важен — мёртвый порт заставляет
   некоторые клиенты падать в прямое соединение.
3. `InternetSetOption` + `WM_SETTINGCHANGE` — приложения подхватывают
   смену прокси на лету.
4. `[allow]`-правила становятся `ProxyOverride` — разрешённые адреса
   идут напрямую, минуя прокси.
5. По выходу — настройки прокси возвращаются как были.

## Использование

```
nl run 60          блок на 60 сек (минимум 30)
nl run             до Ctrl+C
nl run 300 -min    свернуть: отсчёт в заголовке + прогресс-бар
                   на кнопке панели задач
nl run 300 -hide   вообще без окна (остановка — дождаться
                   конца таймера или taskkill + restore)
nl run -wfp        принудительно WFP (нужен админ)
nl run -fw         принудительно COM-firewall (нужен админ)
nl run -proxy      принудительно proxy (даже под админом)
nl fwplan          показать план fw-правил без применения
nl status          права, доступность движков, конфиг,
                   подвисший backup / fw-правила
nl restore         вернуть прокси из backup + снять fw-правила
```

## Конфиг `netlock.ini`

```ini
[main]
seconds = 0          ; 0 = до остановки; минимум 30
engine = auto        ; auto | wfp | fw | proxy

[allow]
192.168.0.0/16       ; CIDR — для WFP и для proxy (в wildcard)
10.0.0.0/8
*.lan                ; wildcard-паттерны — только proxy-режим
intranet.local       ; имена хостов — только proxy-режим
```

CIDR раскрываются в wildcard-октеты: `172.16.0.0/12` →
`172.16.*.*` … `172.31.*.*` (16 записей).

## Отказоустойчивость

- **WFP**: динамическая сессия — фильтры умирают вместе с процессом.
  Крах/убийство = самоотглушение.
- **fw**: правила персистентны — переживают крах. Снимаются при выходе;
  сироты подметаются при следующем `run`/`fw` или `nl restore`.
  `status` сообщает об оставшихся правилах `NetLock-*`.
- **proxy**: крах оставляет блок активным, но `netlock-backup.ini`
  хранит исходные настройки — `nl restore` или следующий
  запуск `run` восстановит их. `status` показывает подвисший backup.

## Чего нет (и почему)

- **Нет службы и автозапуска** — установка службы требует админа.
  Lite живёт только пока жив процесс (в proxy-режиме блок переживает
  крах через реестр, в WFP — снимается автоматически).
- **Нет туннеля** — не нужен: WFP блокирует на уровне ядра, proxy —
  на уровне настроек приложений.
- **Нет IPv6-специфики в proxy-режиме** — прокси применяется
  одинаково; WFP-режим покрывает v4 и v6.
